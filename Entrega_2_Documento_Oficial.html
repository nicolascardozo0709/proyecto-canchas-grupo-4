Resumen Ejecutivo del Proyecto

El presente documento constituye el informe técnico oficial de la Entrega 2: Desarrollo y Pruebas de la Plataforma de Reserva de Escenarios Deportivos. El propósito de este hito consiste en traducir los artefactos de diseño, requisitos IEEE 830 y maquetas de interfaz elaborados en la Entrega 1 en una solución de software completamente funcional, robusta, altamente probada y respaldada por documentación técnica exhaustiva.

La plataforma resuelve la problemática de sobre-reserva (overbooking), desorganización de horarios y falta de trazabilidad en escenarios multideportivos universitarios mediante una arquitectura desacoplada en capas sobre Java 21 LTS y Spring Boot 3.3.4. La solución incorpora un motor transaccional con aislamiento REPEATABLE_READ y bloqueo pesimista PESSIMISTIC_WRITE, autenticación criptográfica mediante tokens JWT y factor de costo BCrypt 12, una interfaz web SPA intuitiva (WF-01 a WF-04) y una suite de 19 pruebas automatizadas con una tasa de éxito del 100%.

2. Reglas de Negocio Críticas y Algoritmo Anti-Colisión

2.1 Prevención Atómica de Sobre-Reserva (HU-07, RNF-02)

El problema cardinal de los sistemas de escenarios deportivos reside en la concurrencia: cuando dos o más deportistas seleccionan la misma cancha en el mismo horario y disparan la confirmación simultáneamente, un sistema sin concurrencia genera colisiones de reserva (overbooking).

Para garantizar de forma matemática y empírica la exclusión mutua, la plataforma implementa una estrategia de control de concurrencia en tres niveles:

  1. Aislamiento Transaccional REPEATABLE_READ: Cada transacción de reserva opera bajo nivel de aislamiento repetible, evitando lecturas sucias y no repetibles durante la evaluación de cupos.
  2. Bloqueo Pesimista en Base de Datos (PESSIMISTIC_WRITE): En el repositorio JPA se instrumenta la consulta de verificación con bloqueo pesimista a nivel de fila mediante SQL SELECT ... FOR UPDATE:
    @Lock(LockModeType.PESSIMISTIC_WRITE) @Query("SELECT r FROM Reserva r WHERE r.escenario.id = :escenarioId " + "AND r.franja.id = :franjaId AND r.fecha = :fecha AND r.estado = :estado") Optional<Reserva> findActiveReservaWithLock(Long escenarioId, Long franjaId, LocalDate fecha, EstadoReserva estado);
  3. Exclusión Mutua Atómica en Capa de Servicio: El método crearReserva(...) en ReservaService se encuentra sincronizado a nivel de hilo, garantizando que el commit de persistencia de Spring se consolide antes de que cualquier otro hilo acceda a la matriz de verificación. Si se detecta una reserva activa, el sistema detiene la transacción y arroja CollisionException (HTTP 409 Conflict).

2.2 Bloqueo Estricto de Fechas Pasadas (HU-08)

Para evitar inconsistencias en el calendario histórico, se implementa una doble barrera de validación: en la capa de presentación, el selector de fechas HTML5 restringe el atributo min a la fecha actual; en la capa de servicios, el DTO valida la anotación @FutureOrPresent y el método crearReserva verifica programáticamente if (request.getFecha().isBefore(LocalDate.now())) throw new BusinessException(...), retornando HTTP 400 Bad Request.

2.3 Cancelación Inmediata con Liberación Atómica (HU-06)

Al invocar el endpoint PUT /api/reservas/{id}/cancelar, el sistema valida que el solicitante sea el propietario de la reserva o un administrador (HU-19). La reserva muta su estado a CANCELADA, registrando la fecha/hora y el motivo. Al cambiar el estado, la franja horaria correspondiente se libera en la matriz de disponibilidad de manera instantánea, permitiendo que cualquier otro deportista la reserve de inmediato.

2.4 Suspensión por Mantenimiento de Escenarios (HU-21)

El administrador dispone de la facultad de alternar el indicador en_mantenimiento de cualquier escenario. Cuando este flag es verdadero, el motor de reservas bloquea cualquier intento de apartado horaria con el mensaje de negocio correspondiente.

3. Arquitectura del Sistema y Código Fuente

3.1 Arquitectura en Capas Desacopladas (Clean Architecture)

El backend fue desarrollado sobre Java 21 y Spring Boot 3.3.4 bajo una arquitectura en capas desacopladas con inversión de dependencias, garantizando alta mantenibilidad y testeabilidad:

backend/src/main/java/com/canchas/reserva/ ├── config/ -> Seguridad Spring Security 6, CorsConfig, DataInitializer, SwaggerOpenApi. ├── controller/ -> Controladores REST semánticos (Auth, Escenario, FranjaHoraria, Reserva). ├── dto/ -> Objetos de transferencia fuertemente tipados con Jakarta Bean Validation. ├── entity/ -> Entidades JPA (Usuario, Escenario, FranjaHoraria, Reserva) con índices DDL. ├── exception/ -> Manejador global @RestControllerAdvice bajo formato RFC 7807 (ProblemDetails). ├── repository/ -> Interfaces Spring Data JPA con bloqueo pesimista (@Lock PESSIMISTIC_WRITE). ├── security/ -> Filtro JwtAuthFilter, proveedor DaoAuthenticationProvider y BCrypt(cost=12). └── service/ -> Lógica transaccional de negocio (@Transactional isolation=REPEATABLE_READ).

3.2 Modelo de Dominio y Persistencia Relacional

El esquema de base de datos relacional (compatible de forma dual con H2 Database para pruebas y MySQL 8.0 mediante Docker Compose) modela cuatro entidades nucleares con claves foráneas e índices de búsqueda optimizados:

  • Usuario: Almacena nombre, apellido, correo institucional único, contraseña cifrada en BCrypt (costo 12), teléfono y rol de seguridad (ROLE_USER o ROLE_ADMIN).
  • Escenario: Modela la cancha con atributos de disciplina deportiva (FUTBOL, TENIS, PADEL, BALONCESTO, VOLEIBOL), superficie (SINTETICA, ARCILLA, PARQUET, etc.), aforo, iluminación nocturna, tarifa por hora y flag de mantenimiento.
  • FranjaHoraria: Representa los bloques fijos de 60 minutos asociados a un escenario con restricción única uq_franja_escenario_hora (escenario_id, hora_inicio) para evitar duplicidad de bloques.
  • Reserva: Entidad transaccional con código alfanumérico único (ej. RES-20261020-XXXXXX), vinculando usuario, escenario, franja, fecha, precio total pactado y estado (CONFIRMADA o CANCELADA).

3.3 Seguridad Criptográfica JWT y BCrypt Cost 12 (HU-13, HU-18)

La autenticación es completamente sin estado (stateless). Al autenticarse satisfactoriamente contra /api/auth/login, el servidor expide un token JWT firmado criptográficamente con algoritmo HMAC-SHA512. La contraseña de cada usuario es protegida mediante un hash unidireccional con sal aleatoria implementado por BCryptPasswordEncoder(12) (4096 rondas de cifrado), cumpliendo con RNF-03 (Seguridad).

6.2 Prueba de Concurrencia Extrema (AntiColisionConcurrencyTest)

Para demostrar formalmente la inmunidad ante sobre-reserva en condiciones de alta concurrencia (RNF-02), se programó un caso de prueba multihilo:

  • Se instanció un pool con 8 hilos concurrentes (ExecutorService).
  • Mediante un CountDownLatch(1), los 8 hilos aguardaron sincronizados y dispararon en el mismo milisegundo exacto una petición de reserva sobre la misma franja, misma cancha y misma fecha.
  • Resultado obtenido: Exactamente 1 hilo completó la reserva exitosamente; los restantes 7 hilos fueron bloqueados atómicamente por el motor de concurrencia arrojando CollisionException (HTTP 409 Conflict).
  • Verificación en base de datos: El conteo confirmó la persistencia de exactamente una reserva en estado CONFIRMADA.

11. Conclusiones y Planificación Hacia la Entrega 3

11.1 Conclusiones Técnicas de la Entrega 2

  1. Solidez del Núcleo Transaccional: La combinación de transacciones con aislamiento repetible y bloqueo pesimista en base de datos erradica de forma definitiva el riesgo de overbooking, garantizando la integridad de datos bajo cargas concurrentes.
  2. Arquitectura Limpia y Extensible: La adopción de Clean Architecture en Spring Boot 3 permite que cada componente (seguridad, servicios, persistencia, controladores) evolucione de manera independiente sin acoplamiento.
  3. Rigor en Aseguramiento de Calidad: La batería de 19 pruebas automatizadas y la colección de Postman demuestran que el sistema no solo funciona en casos ideales, sino que responde de manera segura ante casos de borde (colisiones, fechas pasadas, cancelaciones no autorizadas).
  4. Experiencia de Usuario Fluida: La implementación reactiva de los wireframes proporciona una experiencia ágil tanto para el deportista que aparta una cancha como para el administrador que gestiona el complejo.

11.2 Planificación y Hoja de Ruta para la Entrega 3 (Sprints 4 y 5)

Con el núcleo de reservas consolidado, el esfuerzo del equipo en los Sprints 4 y 5 se concentrará en las siguientes historias de usuario:

  • Módulo de Analítica y Dashboard (HU-09, HU-10): Incorporación de gráficos interactivos con Chart.js para visualizar histogramas de horas pico nocturnas y porcentaje de ocupación mensual por escenario deportivo.
  • Exportación Tabular a CSV (HU-11, HU-12): Generación de reportes de auditoría descargables filtrados por rango de fechas para la administración deportiva.
  • Pruebas de Aceptación de Usuario (UAT): Validación de usabilidad con deportistas y personal administrativo de la universidad.
  • Despliegue Productivo en la Nube: Publicación continua en plataforma cloud (Render/Railway) y preparación de la sustentación presencial final.
